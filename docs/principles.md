# Kizu 設計原理

> 傷を作らない。傷を隠さない。

本書は Kizu の設計判断の原理です。言語と標準ライブラリの具体的な仕様は実装と検査が正本を持ちます——コンパイラ本体([compiler/](../compiler/))、標準ライブラリ([lib/kizu/std/](../lib/kizu/std/README.md))、実行可能な例と振る舞いテスト([examples/](../examples/README.md)・[tests/behavior/](../tests/behavior/))、機械検証される形式仕様([spec/](../spec/README.md))、`kizu lint` です。

API 設計や言語仕様の判断で迷ったら、まず本書の原理に照らします。

## 原理

### 1. 隠れた制御フローと隠れた確保を持たない

実行時のコストや制御の移動は、すべて source に見せます。自動 Drop・暗黙の例外・非同期の関数色付けのように、呼び出しが source に現れない仕組みは持ちません(`defer` や `errdefer` のように呼び出しが source に見えるものは原理内です)。メモリ確保は明示的な allocator を通じ、global / default allocator による hidden allocation を許しません。

### 2. 危険は禁止ではなく、grep できる明示語にする

安全でないものを作らないのが基本です。避けられない危険や境界越えを型で閉じきれないときは、暗黙の既定値や嘘の定数で覆い隠さず、`unsafe` や明示的なモード・関数名といった正直な 1 語に表します。レビューアは明示語を grep するだけで危険の境界をすべて列挙できます。

### 3. 検査は構造とコンパイル時に閉じる

実行時の発見や説明コメント・散文ドキュメントに頼る前に、型・所有権・状態機械(`std::machine`)・形式検証([spec/](../spec/README.md))・conformance test・`kizu lint` で機械的に閉じられないかを先に問います。GC も複雑なライフタイム注釈も持たず、ローカルに読める move / borrow / 明示 cleanup の規則でメモリ安全を静的に保証します。

### 4. 意味に従い、余計な区別も曖昧な統合もしない

意味が同じなら新しい型や構文を増やさず、既存の規則で表します。逆に原因・回復・契約が異なるものは、同じ名前・型・error に畳みません。意図の表現は素直で一通りに保ち、call site ごとに定型が量産される設計は定義側へ 1 行に畳みます——ただし、制御フローやコストを隠す自動化はしません。

### 5. 可逆性の非対称で決め、迷ったら閉じたまま出す

閉→開は additive、開→閉は breaking です。公開範囲・拡張点・契約化・暗黙の許容は、実需が確認されてから開きます。

### 6. 実装は 1 つ、実行経路は 1 本

利用者が通るコンパイラ実装と意味論の経路は 1 つに保ちます。interpreter、hidden fallback、削除条件のない互換分岐は持ちません。`kizu run`・`kizu test`・`kizu build` は同じ lowering を通り、ネイティブ・Wasm・GPU を含む各ターゲットは共通の型付き SSA IR から出力します。ターゲットが持たない capability は暗黙に誤魔化さず、明示エラーで拒否します。

### 7. コンパイラを形で特殊化せず、速さと self-host を規律にする

ソースの形ごとの payload 型・関数名分岐・形状 template を作りません。機能追加がコンパイル時間やキャッシュ効率を悪化させるなら設計を疑います。ビルドと開発サイクルの速さそのものを言語の機能とみなし、前リリースの種([scripts/seed.txt](../scripts/seed.txt))から自分自身を再現できる self-host 規律を保ちます。
