# Kizu 設計原理

本書は Kizu の設計判断の原理です。`SPEC.md` は言語の定義、ADR は個々の決定の
記録で、どちらも本書の原理を個別の問題に適用した結果です。

API 設計や仕様判断で迷ったら、まずここに照らします。

## 原理

### 1. 傷を作らない。傷を隠さない。

安全でないものを作らない。避けられないコストや危険は、消したふりをせず source に
見せる。以下の原理はすべてこの言い換えである。

### 2. hidden control flow とは「呼び出しが source に見えないこと」

`defer x.deinit()` は呼び出しが見えるので原理内。自動 Drop は見えないので違反。
生成された body でも、呼び出し自体が source にあれば隠れていない。

### 3. 危険な選択は禁止ではなく、grep できる明示語にする

`mem::Limit::Unlimited`、`mem::leak(x)`、`unsafe`。危険を型で禁止できないとき、
嘘の数値(maxInt を渡す定型)より正直な単語 1 語を選ぶ。review は明示語を grep
すれば危険な箇所を列挙できる。

### 4. 確保は明示 allocator。hidden allocation を持たない

allocator を受け取らない API が内部で確保するのは違反。global / default allocator
は持たない。

### 5. 型で閉じられる検査は compile 時に閉じる

runtime 検出やテストの網羅性に頼る前に、型 error にできないかを先に問う。
owner 要素 collection の cleanup 強制がこの形。

### 6. 型を増やして Kizu ユーザーに区別を課さない

新しい区別が必要に見えたら、既存型の規則で表せないかを先に問う。

### 7. 意味が違うなら、違うものにする

原因・回復・契約が異なるものを、同じ名前や同じ型や同じ error に相乗りさせない。
limit 超過(入力を拒否して回復する)と OutOfMemory(確保に失敗した)は別 error。
原理 6 と対になる: 区別は意味の差にだけ従う。意味が同じなら増やさず、意味が
違うなら畳まない。

### 8. 可逆性の非対称で決める。迷ったら閉じたまま出す

閉→開は additive、開→閉は breaking。Kizu ユーザー向けの拡張点(contract 化、
公開範囲)は実需が現れてから開く。

### 9. 実装は 1 つ、経路は 1 本

第二実装、hidden fallback、削除条件のない互換分岐を作らない。interpreter は
持たない。

### 10. 定型が量産される設計は間違っている。定義側 1 行に畳む

同じ定型が call site の数だけ増える案は却下し、宣言側で 1 行にする。ただし
畳んでよいのは情報量が同じ場合だけで、原理 2 を破る自動化はしない。

### 11. compiler を形で特殊化しない。ビルドと開発サイクルの速さは機能

ソースの形ごとの payload 型・関数名分岐・形状 template を作らない。機能追加が
コンパイル時間を悪化させるなら設計を疑う。
